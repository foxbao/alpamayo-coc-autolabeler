# `v_lat` 左右符号约定问题梳理

## 文档目的

记录自动标注代码中横向速度 `v_lat` 的坐标变换、投影公式、提示文字和数据核验情况，供独立评审。本文先整理问题和证据，再记录评审后的实施决定。

## 问题是怎么发现的

讨论 PAI-AV 输入给 Agent 的信息时，我们注意到代码一边计算 `v_lat`，一边在提示中解释它的正负方向。公式与提示里的方向似乎相反：按仓库坐标变换和公式推导，公式的正方向沿车辆左侧；提示却写正值表示向右。

随后我们尝试用 PAI-AV 的明显横移片段核实。找到的候选片段要么横向速度很小，要么同时处于弯道；车道变更方向也不能直接代表相对车身的瞬时横向速度。因此，视频没有提供足够干净的符号真值。问题由此从“提示是否写反”扩大为：代码约定、数据坐标和希望 Agent 理解的语义是否一致。

## 发现问题时的仓库实现

相关代码位于：

- `src/coc_labeling/data_loader/trajdata.py`：读取 `trajdata` 的位置、航向与速度；将位置和速度的两个平面轴交换，并将新 x 轴取反。注释描述变换后的轴为 `x→右、y→前`。航向加 `π/2`，随后由变换后的速度和航向计算纵向、横向速度。
- `src/coc_labeling/data_loader/vector_loader.py`：把速度序列写入 Agent 文本，并说明“正横向速度向右，负值向左”。
- `src/coc_labeling/prompts/vlm/coc.py`：运动状态提示也说明“正 lateral 向右，负 lateral 向左”。

设变换后的速度为 `(vx, vy)`，航向为 `h`。**发现问题时的旧公式**为：

```text
v_long =  vx·cos(h) + vy·sin(h)
v_lat  = -vx·sin(h) + vy·cos(h)
```

这两个分量分别是速度在以下两个单位方向上的投影：

```text
车头方向       e_forward = ( cos(h),  sin(h))
车头左侧方向   e_left    = (-sin(h),  cos(h))
```

因此按标准二维数学角度“从 +x 逆时针量取”的解释，旧公式的 `v_lat` 是**左正**。若要定义为右正，对应投影方向是 `e_right = (sin(h), -cos(h))`，公式为：

```text
v_lat_right_positive = vx·sin(h) - vy·cos(h)
```

两种公式只差一个负号。右手坐标系本身并不决定横向标量必须左正还是右正；项目需要选定一种约定，并确保计算、提示、测试和下游使用一致。

### 直行时的例子

变换后的轴是 `x→右、y→前`。直行时车头朝 `+y`，对应 `h=π/2`：

| 运动 | 变换后速度 `(vx, vy)` | 当前公式（左正） | 右正公式 |
|---|---:|---:|---:|
| 向前 | `(0, 1)` | `0` | `0` |
| 向左 | `(-1, 0)` | `+1` | `-1` |
| 向右 | `(1, 0)` | `-1` | `+1` |

容易产生困惑的点是：世界/目标坐标的 `+x` 的确朝右，但 `v_lat` 并非直接取 `vx`。它先根据车头航向定义车体横向轴，再将速度投影到该轴。直行时，旧公式的左正车体横向轴是世界坐标的 `-x`，所以右移 `(1,0)` 在旧公式下得到负值。这在数学上自洽，但与项目提示采用的右正约定相反，也不符合我们希望 `x` 向右时横向正值直观表示右移的选择。

## 还需要核实的坐标来源

`trajdata.py` 注释记录了输入状态的轴为 `x→前、y→左、z→上`，变换后为 `x→右、y→前、z→上`。本机 `alpamayo-coc` 环境安装的 `trajdata` 包中，`trajdata/data_structures/state.py` 的 `lat_component` 定义为 `-x·sin(h) + y·cos(h)`，注释说明这是沿 heading 垂直方向 `(-sin(h), cos(h))` 的投影。按常见的 heading 从 +x 逆时针定义，这也是左正分量。

这能解释旧公式为什么是左正。Agent 现在采用右正约定；若要继续审查上游和其他模块，重点是确认这些接口契约：

1. PAI-AV 原始 `egomotion` 中 `x/y/vx/vy` 和四元数的具体参考系、轴方向及时间语义是什么。
2. `trajdata` 对 PAI-AV 的转换是否与仓库注释中的输入轴、heading 角定义完全一致；速度向量和航向是否处在可直接投影的同一坐标系。
3. 是否还有直接消费 `trajdata` 原生 `lat_component` 的调用方，需要保留它的左正定义。
4. meta-action、评估代码或模型接口是否依赖另一种横向符号；当前搜索到的 lane processor 使用独立的车道相对左正量。

## 评审后的实施决定

评审确认了两件需要分开处理的事情：

1. 当前原始投影公式是沿车头左侧的**左正**定义；而 Agent 提示已经采用“正值向右”。继续保留两套说法会让同一组数值产生相反解释。
2. `v_lat` 是速度在车体瞬时横向轴上的投影，也就是 vehicle/body-frame lateral velocity。它不是车道中心相对位移，也不是“向左/向右变道”的行为标签。正常行驶时它可以接近零，即使车辆正在完成明显的变道；转弯时它也可能受航向变化影响。

本轮采用**右正**作为给 Agent 的横向速度契约，因为它与变换后的 `x→右、y→前` 坐标、当前提示文字和直观使用方式一致：直行时右移 `(1, 0)` 对应 `v_lat=+1`，左移 `(-1, 0)` 对应 `v_lat=-1`。右正投影为：

```text
v_long =  vx·cos(h) + vy·sin(h)
v_lat  =  vx·sin(h) - vy·cos(h)
```

实现集中在 `src/coc_labeling/data_loader/motion_conventions.py`，生产轨迹转换、速度文本和 VLM 提示共同引用它的约定。`tutorials/18_mini_loaders.py` 和 `tutorials/19_handwrite_messages.py` 也同步到同一语义。

这会使 Agent 使用的 `v_lat` 与 `trajdata` 包内部 `lat_component` 的左正命名相反。代码注释明确写出这一层适配，避免以后把两者直接对比时再次混淆。`meta_action/processor/lane/segmentation.py` 中的 lane 横向位移仍然是独立的“左正”车道语义；它不读取这个 `v_lat`，本轮不修改。

提示措辞改为“body-frame lateral velocity”，并明确它不能单独表达变道方向。需要判断变道或绕障方向时，仍以视频、车道先验和 lane/meta-action 信息为主。

## PAI-AV 样本核验情况

样本数据放在本机目录 `/home/baojiali/Downloads/pai_av_lateral_check`，不是仓库文件，也没有提交到版本控制。

- Clip `00763228-8e24-43b6-90f4-43539e492695`（chunk 1517）带有“向左变道”CoC 描述。前视视频可见车辆向左变道，位置轨迹也随道路/航向变化；但按改动前公式，事件附近瞬时 `v_lat` 接近零。车辆主要沿转弯后的车头方向行驶，所以这个样本能确认可见的变道/路径方向，却不能直接确认横向速度正负。
- Clip `1d36d71a-5a5a-4e2e-8124-bb8682bfb3cd`（chunk 658）也带有向左变道描述，但视频显示处于施工区域弯道，航向变化很大。按改动前的左正公式，事件附近出现一定的负横向速度；弯道曲率和方向变化使它不能作为清楚的左移符号真值。
- 另一些候选 clip 有更大的横向速度，但视觉上处于连续弯道；还有候选只呈现“相对前车从一侧通过”的间接证据。它们都不足以单独判定 PAI-AV 的横向分量语义。

所检查的 PAI-AV 样本中，原始位置差分与速度字段相互吻合；样本也说明变道方向不能作为 `v_lat` 的直接真值。符号选择属于项目给 Agent 的标量约定；本轮通过统一公式、提示和单元测试固定为右正，而不是声称从视频中测出了一个独立的 `v_lat` 标签。

## 为什么模型结果看起来仍合理

“推理输出合理”不能用于证明 `v_lat` 符号正确。Agent 同时接收视频和轨迹信息；当横向速度很小、转弯让横向分量难以解释时，模型可以依靠画面、轨迹位置和其他输入判断行为。官方 Alpamayo PAI-AV loader 使用位置和姿态构造轨迹，也没有直接读取名为 `v_lat` 的独立数据字段。因此，能完成推理或生成合理 CoC，不表示左右速度符号已核实。

另外，以下语义需要分开：

- `v_lat`：速度在车辆瞬时横向轴上的投影，描述相对车身的瞬时横移分量。
- 向左/向右变道或绕障：沿道路/车道语义描述的行为。变道过程中车头会转向；行为方向不必与每一时刻的车体系横向速度符号一一相同。
- 地图/世界坐标中的 `vx/vy`：需要先确认参考系，再根据姿态变换到车体轴；不能仅看列名推断左右语义。

## 后续仍可核验的边界

1. 如需确认上游数据契约，应继续核对 PAI-AV schema 与 `trajdata` PAI reader 对位置、速度、quaternion 和 heading 的坐标解释。
2. 若 Agent 需要识别变道或绕障方向，应以视频、lane/meta-action 等道路语义特征为依据；不要把 `v_lat` 当成替代品。
3. 若未来需要显式提供“相对车道中心线的横向偏移/变化率”，应将它定义为独立特征，并单独说明其参考线、坐标方向和符号，不要与 body-frame `v_lat` 混用。
