# 本地定位坐标到 CoC 速度输入

本文记录 `/home/baojiali/Downloads/disk3/20261019_lin_007_out` 中四条本地记录的坐标核对结果，以及本地标注器采用的速度转换。原始 localization JSON 没有写明坐标系标签，因此本文按这批数据中的轨迹、规划结果和前视画面作判断；不从旧版定位软件源码推断当前数据格式。

## 当前判断

这批记录按 **FLU** 解释最符合数据表现：车体局部 `x` 向前、`y` 向左、`z` 向上。对应 CoC 输入为：

```text
v_body_flu = R(q)^T · [v_map_x, v_map_y, 0]
v_long = v_body_flu.x                 # 前向为正
v_lat  = -v_body_flu.y                # 右向为正；FLU 的 y 向左
v_ground = sqrt(v_map_x² + v_map_y²)  # 水平速度大小
```

这里的 `R(q)` 把车体局部坐标转到定位位置使用的 map-XY 坐标。文件名时间戳仍作为采样时间；位置差分提供 map-XY 速度，姿态四元数只负责将它投影到车体坐标。`v_lat` 是瞬时车体右向速度分量，不等同于变道方向。

## 用这批记录核对的依据

定位 JSON 中只有 `position`、`orientation`、`linear_velocity` 等数值字段，没有 `FLU`、`RFU`、父子坐标系或生产程序标识。因此，数值本身无法直接给出局部 `x/y` 的物理名称。我们用多种数据线索交叉判断：

| 记录 | 有效运动样本 | 中位地速 | 地图轨迹方向与四元数 yaw 的绝对角差中位数 / P90 |
|---|---:|---:|---:|
| `153841` | 18 | `1.96 m/s` | `1.10° / 3.35°` |
| `153911` | 29 | `2.51 m/s` | `4.15° / 23.40°` |
| `153941` | 39 | `5.77 m/s` | `0.37° / 0.75°` |
| `154011` | 25 | `2.99 m/s` | `0.18° / 0.62°` |

统计使用 0.5 秒中心差分、每 0.5 秒取一个运动样本，并剔除地速低于 `1 m/s` 的点。尤其在 `153941` 和 `154011` 中，地图轨迹方向持续贴近四元数的局部 `x` 方向。`153941` 的事件时刻还满足：地图轨迹方向约 `−7.28°`，四元数 yaw 约 `−7.20°`，同刻规划轨迹的 `theta` 约 `−7.52°`、规划速度为正 `5.66 m/s`。

前视相机也提供独立的运动线索：在 `153941` 事件前后连续的 15 对、间隔 0.5 秒的图片中，跟踪到的静态背景特征在图像左侧总体向左移动、右侧总体向右移动，表现为向外展开。这与相机沿视线前进相符；若是相机整体向右横移，背景水平运动通常会以同一方向为主。该判断依赖 `camera/front` 的安装朝向，属于视觉核验线索，不是坐标标记。

按当前 10 Hz 重采样及 0.5 秒中心差分流程，`153941` 事件时刻的位置差分约为 `v_long=+5.59 m/s`、`v_lat=+0.01 m/s`，地速约 `5.59 m/s`。因此先前约 `5.6 m/s` 的“向右速度”是把局部 `x` 轴误当成右轴造成的；这段运动更符合沿车体前向行驶。

## 速度字段的限制

`linear_velocity.x/y/z` 没有记录坐标系或 producer 信息，不能只靠字段名判断它属于 map、FLU 还是 RFU。不过，对四条记录的逐样本核对强烈支持它的**水平分量**是车体 FLU：先按 `x=前、y=左` 将 `linear_velocity.x/y` 用 orientation 旋转到 map，和位置差分速度的方向及向量残差明显优于把原值直接当作 map-XY 速度。当前数据还没有独立证据确认该字段的 z 轴正方向；`z=上` 是 FLU 表述下的工作假设。

坐标诊断在每个有效 localization 时间戳上比较 `linear_velocity.x/y` 与 0.5 秒中心差分得到的 map 速度，只保留位置地速和原始水平速度都大于 `1 m/s` 的样本。方向栏是候选速度方向与位置轨迹方向之间的绝对角差中位数 / P90；残差栏是速度向量差的中位数：

| 记录 | 样本数 | 原值按 map-XY：角差中位数 / P90 | 按 body-FLU 经 orientation 旋转：角差中位数 / P90 | 向量残差：map / body-FLU (m/s) |
| --- | ---: | ---: | ---: | ---: |
| `153841` | 2,128 | `28.73° / 40.12°` | `2.16° / 3.55°` | `0.936 / 0.093` |
| `153911` | 3,028 | `8.59° / 9.56°` | `1.52° / 2.51°` | `0.345 / 0.064` |
| `153941` | 3,241 | `8.99° / 9.52°` | `1.65° / 2.16°` | `0.854 / 0.152` |
| `154011` | 2,571 | `9.01° / 9.76°` | `1.63° / 2.39°` | `0.451 / 0.077` |

横向符号方面，0.1 秒位置差分得到的 body-left 分量与原始 `linear_velocity.y` 在 `153841`、`153911` 的相关系数分别为 `0.992`、`0.997`，支持 y 轴同为左正；另外两条相关性较弱（`0.760`、`0.672`），且原始 y 相对推导 body-left 的中位偏差约 `+0.06` 至 `+0.14 m/s`。因此水平 `x` 前向、`y` 左向是目前最有数据支持的解释，但横向分量仍存在小偏差，z 轴符号未独立核实，且生产端契约缺失。

这仍是数据驱动的工作假设，不是 JSON 或 producer 提供的正式契约。当前 `linear_velocity` 只用于审计，不直接送给 Agent；`153941` 事件附近的原始水平分量约为 `(5.62, 0.13) m/s`。

## 代码中的处理

`recording_autolabel/localization.py` 执行以下步骤：

1. 将原始位置插值到 10 Hz 网格；相邻原始样本间隔超过 32 ms 时保留缺失点。
2. 对 10 Hz map-XY 位置作 0.5 秒中心差分，得到 map-XY 平面速度和地速大小。
3. 在同一时刻对姿态四元数作 SLERP，并用逆旋转得到车体 FLU 分量。
4. 把 `body_x` 作为 `v_long`，把 `-body_y` 作为右正 `v_lat` 输入 Agent；`v_ground` 只保存在审计产物中，不发给 Agent。
5. 在 `position_motion_audit.json` 中保存使用的坐标解释、地图速度、姿态、推导的 FLU 分量、原始 `linear_velocity`（强支持车体 FLU 的工作假设）和一致性残差。

FLU 是这四条记录上的数据驱动判断，不是 localization JSON 自带的契约。如果将来输入来自不同车辆、相机安装方向变化或定位生产链路变化，应先重新做同类核对，再使用这些车体分量。旧的 RFU 版本审计 JSON 也需要重新运行生成，不能与新字段语义混用。
